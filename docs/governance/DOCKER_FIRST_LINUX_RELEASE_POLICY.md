# Docker-first Linux release qualification policy

**Status:** Effective governance clarification (merged PR #362); Release 1.15 architecture details remain under review in PR #361.  
**Scope:** AIQuantTradingResearch public application; preserve Release 1.14 synthetic qualification history and support a separately authorized Release 1.15 historical crypto-chart candidate.  
**Target:** Azure App Service **Linux F1** custom container.  
**Authority:** Qualification policy only, not implementation, provider, release or deployment authorization.

## Decision and intent

The canonical release-qualification environment is the **actual Linux Docker image intended for deployment**. Windows may be a development workstation but is not a production/certification runtime. Build and qualify one immutable image and, only after separate approval, promote its exact digest.

## Binding rules

1. **Container-only release acceptance.** Functional, integration, browser, security, filesystem and startup evidence MUST exercise a locally executed Linux image. Windows host-only evidence does not certify the public runtime.
2. **One immutable deployable image.** Record source/build provenance and image digest; do not rebuild or substitute bits between qualification, registry promotion and Azure deployment. Promotion and deployment each require separate authorization.
3. **Runtime profiles are release-specific.** For the historical Release 1.14 synthetic showcase, prefer the existing single-process Streamlit/Plotly runtime with approved immutable synthetic handoff and offline C# calculations. For a **separately authorized Release 1.15 historical candidate**, a **single image with a minimal PID1 supervisor and two isolated non-root processes**—private C# ingestion/research and public Streamlit/Plotly—is an allowed architecture, subject to the Release 1.15 governance and qualification gates. This architecture allowance does not itself activate a provider or authorize deployment.
4. **Dataset and source policy.** The Release 1.14 synthetic handoff remains checksummed, immutable and clearly synthetic. The Release 1.15 design uses bounded, private SQLite historical data and clearly labeled transformed public presentation. Provider licensing is not an implementation milestone or approval gate in this release. Never package provider credentials, private replay, raw restricted candles or secrets in publicly readable image assets or public routes. Do not treat HMAC transformation as a license.
5. **Linux runtime security.** Verify correct PID1/supervisor behavior, restart limits, health/startup, public port 8501, separate non-root identities, strict file/secret permissions, SQLite/WAL/checkpoint isolation, loopback-only private API, public process environment sanitization, bounded memory/CPU/PID use and concurrent access. Test that the public identity cannot read research-only files/secrets or reach private services from external ingress. No unplanned outbound network; configured ingestion egress must be bounded, observable and covered by runtime security tests.
6. **Browser acceptance on container.** Use a real browser against the running Linux image. Release 1.14 tests cover synthetic candles, volume, range/interval, technical analysis, hover, zoom, pan and toolbar. Release 1.15 tests additionally cover BTC/USD and ETH/USD selection, indicators, historical viewport retention, reconnect/disconnect and last-known data, corrections/intervals, truthful transformed labels and status. Use deterministic isolated fixtures; no live provider dependency in CI.
7. **No Windows parity mandate.** Native Windows runtime or browser parity is not a release gate; historical Windows evidence may inform debugging.
8. **Provenance and repeatability.** Record source commit, Docker inputs, immutable digest, approved dataset provenance/manifest where applicable, commands, results, observed limits, failures and cleanup. Distinguish environment configuration from image bits.
9. **Per-site Azure verification.** After separately authorized deployment, verify exact digest, configuration, health, resource use, browser UX, API status and rollback at each Azure F1 site. Local F1-like limits are screening evidence, not Azure F1 capacity proof.
10. **Minimalism and change control.** No extra paid service, Windows compatibility program, public private API, provider integration or security exception merely to satisfy qualification. Deviations require explicit owner approval and scoped PR.

## Release gates and non-authorizations

This policy governs **where and how** qualification is performed, not who authorizes release. Preserve G-B0–G-B7, WP07, provenance, dataset readiness, security, immutable image promotion and owner approvals. Do not introduce a provider-licensing prerequisite into Release 1.15 implementation milestones. On conflict, stop and request owner disposition; do not bypass gates.

Release 1.14's existing synthetic image and evidence remain historical and must not be silently mutated. C2B-32 remains ABORTED; C2B-31 remains DEFERRED. The proposed Release 1.15 dual-process runtime is a **candidate**, not a deployment authority. Until separately authorized and independently qualified, `PUBLIC_RUNTIME_VERIFIED=False`, public deployment/activation **NO-GO**, and advanced WP07 **ON HOLD**. Preserve existing unavailable public-API behavior where applicable.

## Release 1.15 two-container amendment — 2026-10-23

**Owner-selected target:** Release 1.15 replaces the previous single-image, in-container two-process supervisor exception with **two independently deployed immutable Linux/amd64 Docker images per environment**: one C# research/ingestion image and one Streamlit/Plotly UI image. Each image runs one principal application as a non-root identity. No custom C/Bash multiprocess supervisor, retained-root role-switching supervisor or independent in-container application-role restart is required. Container startup/shutdown/restart is the individual platform/container responsibility. This paragraph supersedes the conflicting single-image/supervisor requirements in this policy for Release 1.15 only; Release 1.14 historical qualification is unchanged.

**Qualification and promotion:** Qualify both images as an interoperating, version-compatible pair. Record separate immutable digests, source/build provenance, test configuration and the exact paired digests qualified. Independent rollouts must preserve compatibility or use an explicit rollback/coordination plan. Each image and each of the four Azure App Services requires separately authorized deployment and Azure verification; successful creation of an empty Web App is infrastructure evidence, not application availability.

**Topology:** In West Central US production, keep the existing UI Web App `aiqr112wp035ec325382770` and use the newly created research Web App `aiqr115researchprodwcus7f5eabb5` on existing Linux F1 plan `asp-aiq-r112-wp03-wcus-5ec325382770`. In West US 2 staging, keep UI Web App `aiqr112wp05wus27f5eabb5` and use new research Web App `aiqr115researchstagingwus27f5eabb5` on `asp-aiq-r112-wp05-wus2-7f5eabb5`. Exactly two apps share each existing plan and therefore shared Free-tier resources/quotas; no dedicated capacity is implied. Infrastructure observations are documented in [Release 1.15 Azure F1 evidence](../roadmap/release-1.15/RELEASE_1.15_AZURE_EXISTING_F1_PLANS_CAPACITY_EVIDENCE.md) in open PR #381; until merged, treat that evidence as pending PR content.

**Research API boundary:** No cross-Web-App loopback or private network claim. UI-to-research requests cross a network boundary and must use HTTPS, authenticate the calling service, be authorized for only bounded transformed read-only snapshot/status operations and reject unauthenticated or direct unauthorized access. Do not send raw candles, SQLite data, ingestion credentials, HMAC keys or administrative actions to the UI. Under F1, VNet integration/private endpoints and a private DNS route are **not assumed**; evaluate a least-privilege F1-compatible ingress/authentication mechanism in WP02/WP05 with Azure proof in WP07. A research app's public hostname must never be described as private ingress. Do not activate a publicly reachable research API until the approved access control and transport are verified. Keep future policy/transport choices scoped, rather than adding a paid gateway, network resource or plan upgrade by default.

**Isolation and continuity:** Research owns its private storage, SQLite writer, recovery evidence and secrets; the UI image receives none of those volumes or credentials. Enforce least-privilege non-root execution and secret-free UI image/configuration. Health, restart, crash recovery and service outage semantics are per App Service, with truthful UI disconnected/last-known behavior. Cross-instance and rollout overlap can duplicate research writers even if each App Service normally runs one app instance; WP03/WP07 must demonstrate exclusive authoritative storage writer and recoverable lineage before activation. Qualify F1 idling, cold starts, CPU/memory contention and separate-role operation rather than assume shared-plan headroom.

**Compatibility interpretation:** Older text in this file calling for “one immutable deployable image,” “PID1/supervisor behavior,” “two isolated processes,” or a “loopback-only private API” describes the superseded Release 1.15 design. Apply the two-image and authenticated-cross-app requirements of this amendment instead. Continue Docker-first Linux qualification, local browser tests, historical gating G-B0–G-B7, owner approval, no licensing implementation prerequisite, and `PUBLIC_RUNTIME_VERIFIED=False` until actual independently qualified runtime evidence exists. No deployment, new Azure resource, source code or provider activation is authorized by this amendment.
