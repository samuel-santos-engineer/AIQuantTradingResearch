# Release 1.15 WP49 - Exchange-origin OHLCV evaluation and WP50 design

Date: 2026-11-08 (America/Sao_Paulo). Documentation evaluation, not provider qualification.
Baseline: merged PR #435, `7c8d242105fbc5e3fbed4159b07f94a90a7a271c`.

## Decision

**Rank 1 / primary recommendation: Kraken Spot REST OHLC for a bounded recent-history bootstrap.** Official evidence supports actual BTC/USD and ETH/USD spot markets and base-asset traded volume. This selects a design candidate, not an operational source. Twelve Data remains the existing implementation.

**Coverage limitation:** Kraken cannot return 1,000 closed one-minute candles or a full recent 24 hours through this endpoint. It returns at most 720 entries including an unfinished candle; at most 719 are closed, and the grace filter can reduce that further. The repository's 1,000 rows and 24 hours are upper bounds, not promises of complete coverage. Choosing this bootstrap must not be described as satisfying a complete 1,000-candle view. The existing 1,000 preset can display only available observations. If complete 1,000-minute coverage is required, Kraken REST is unsuitable; rank 2 needs its remaining contract clarification, or a separately chosen historical archive window. No pagination can repair Kraken's retention limit.

**Rank 2: Coinbase Exchange REST**, with stronger historical window paging but weaker explicit minute-endpoint volume-unit documentation in the reviewed sources. Do not borrow volume semantics from a different Coinbase product as conclusive proof. **Rank 3: Kraken downloadable OHLCVT**, useful for a reproducible historical chart but not the latest window. No other exchange materially improves this evidence without expanding the investigation.

## API versus archive and finite request plans (not executed)

Kraken's first-party OHLCVT CSV has timestamp/open/high/low/close/volume/trades, no header, and minute files among its supported intervals. Quarterly large multi-part history is less practical than two small API responses for the initial recent chart. A frozen historical window would offer better reproducibility and potentially complete 1,000 rows, but requires explicit selection of a past window rather than pretending it is current. No archive, manifest or checksum asset was downloaded. Trade archives would also require new aggregation work and are not recommended for WP50.

Coinbase Marketplace involves purchased downloads and does not list one-minute OHLCV among the reviewed hourly/daily products. It adds account/download work without resolving the initial chart's minute contract; do not adopt it here.

Proposed Kraken plan: freeze one UTC anchor T, then BTC/USD followed by ETH/USD, one GET each, interval=1, since=UnixSeconds(T minus 24 hours), assetVersion=1. Use the exact Spot base `https://api.kraken.com/0/public/OHLC`; query pair aliases `XBTUSD` and `ETHUSD`. Kraken's official [C# example](https://support.kraken.com/cn/articles/4407678695316-example-code-for-c-rest-and-websocket-api) uses ethusd/xbtusd; request alias and returned display key are distinct. Accept only corresponding `BTC/USD` or `ETH/USD` result key with assetVersion=1, plus last. Do not discover arbitrary pairs or query AssetPairs during acquisition. No credentials, private endpoints, unsupported limit parameter, retries or backfill. Space starts by at least one second; stop after any failure. Proposed cap: two total sends, five seconds per HTTP operation, 1 MiB streamed response bound each and 40-second parent budget, cancellation propagated. These are future implementation limits, not measured timings.

Alternative Coinbase design: GET `https://api.exchange.coinbase.com/products/BTC-USD/candles` and equivalent ETH-USD with granularity=60 and explicit UTC start/end. Four adjacent 250-minute windows per pair cover 1,000 minutes: **eight calls total**, not the existing two-call contract. A full 1,440-minute day requires six bounded windows per pair, **12 calls**. Filter boundary overlap/out-of-window rows, sort and reject conflicting duplicates. Sparse intervals mean these counts do not guarantee that many rows. No automatic switch or pagination is authorized; selecting this alternative requires a reviewed request-budget change and clarification of REST minute volume units.

Normalization design: validate eight-field REST tuples as timestamp/open/high/low/close/VWAP/volume/trade count; the reviewed REST example demonstrates positions but does not expose all expanded tuple semantics in browser text.
